# Forge Endless World, Phase 3: v5 Saves, Column Store and Placed Flags Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Save a world as its generator settings plus a delta per edited column — `0xFF` for "as generated", run-length encoded — in a v5 document for files and share hashes, and in IndexedDB `cc_worlds` version 2 with a per-column store written in one transaction per save. Survival placed-by-player bits move into the world, one bitset per column, and are saved with the column's delta, so a reload no longer turns placed blocks back into natural ones. Every v4 world, file and share hash keeps opening. Worlds are still the bounded 128 box, so every column stays resident and the delta path is proved where nothing streams.

**Architecture:** `World` gains `edits` (column key → saved delta), `dropped` (tombstones for deltas that went away) and a counter, `editRev`, that stamps both. A new module, `src/world/world-delta.js`, diffs a column against `generateColumn` (`columnDelta`), lays a delta back over generated bytes (`applyDelta`), folds every modified resident column into `edits` (`foldEdits`) and rebuilds resident columns from the generator plus `edits` (`restoreColumns`). The codec writes v5 as `{version: 5, meta, columns: [[cx, cy, overlay, placed?], …]}` and reads v5, v4 and legacy maps. The store keeps one `worlds` row per world (meta, no blob) and one `columns` row per delta; `world.persisted = {store, id, rev}` records what the store already holds, so a save sends only deltas and tombstones stamped after it. `SurvivalSession` forwards its placed-bit calls to the world it is attached to.

**Tech Stack:** Vanilla ES modules, Vite, Vitest (unit), Playwright + Chromium with GPU flags (e2e).

**Spec:** `docs/superpowers/specs/2026-09-22-forge-endless-world-design.md`, "Delivery in phases", phase 3; §10, §11, §12, §13; Testing, "Codec and store" and "Survival". The "Decisions (answered 2026-09-22)" section overrides the body. Decision #1 changes §11: a v4 world is not bounded for good but is to expand seamlessly later, so this phase must keep it working bounded *and* keep everything a blend band will need. Decision #2 (optional bounds) is phase 4's.

## Global Constraints

- Branch off `feat/v0.8.0`. Never commit to `master`. Conventional Commits, no AI attribution.
- Generator v1 is frozen; nothing here touches `column-gen.js`.
- `rleEncode`/`rleDecode` keep their output; `NO_EDIT = 0xFF` is reserved (block ids are 0..18).
- `get`/`set`/`inBounds`/`topSolid` and the codec's `packWorld`/`unpackWorld`/`toShareHash`/`fromShareHash` keep their signatures. `encodeWorld` now writes v5; the v4 writer survives as `encodeV4` for tests and fixtures.
- v4 rows, `.ccw` files and `v4.` hashes open forever; `decodeWorld` keeps routing non-versioned objects to the legacy converter.
- Worlds stay bounded: no streaming, no endless worlds, no Endless/Bounded choice (phase 4).
- No new dependencies. There is no `fake-indexeddb`, so the IndexedDB upgrade is proved through `MemoryBackend` in unit tests and against real Chromium IndexedDB in e2e.
- Do not touch campaign/story, audio or `src/ui/hud*.js` files.
- Baseline to hold: 1,203 unit tests across 80 files; `tests/forge.spec.js` and `tests/smoke.spec.js` green.

## Migration and decision #1

- **v4 with no `meta.gen`** (every world saved before phase 2): decodes into the default 128 box with `meta.gen = {kind: "void", seed, v: 1}`, the seed drawn on that first open (decision #1's "given a seed on first open"). A void generator makes air, so every non-air cell is an edit and all 64 columns are stored as deltas — the full content, generator-independent in effect, which is what a blend band needs to read the old edge heights. `meta.bounds` stays unwritten, as phase 1 decided for the default box, so phase 4 can tell "a void world's authored area is its default box" from a bounds the player chose.
- **v4 with a valid `meta.gen`** (worlds made in phase 2): keeps its generator. Its columns are diffed against generator v1, so only its real edits are stored.
- **Legacy 2D maps**: unchanged converter, then the same "no `meta.gen`" rule.
- **In the store**, a v4 row (`bytes`, no `meta`) loads through the codec. The next save of that world writes its `worlds` row without `bytes` and all its column rows in the same transaction, so the blob goes as the columns arrive.
- The seed of a migrated void world is unused until phase 4; it only has to be stable once saved.

## Review Focus

1. **A save that loses a delta.** `foldEdits` runs synchronously before the backend is awaited; a failed commit leaves `persisted.rev` where it was, so the next save sends the same deltas again. *(Tasks 1, 3)*
2. **Deletions.** A column restored to exactly what the generator makes loses its delta, and the store row must go in the same transaction. *(Tasks 1, 3)*
3. **Placed bits and `_adopt`.** `_adopt` used to `resetPlaced()`; now it must *attach* the session to the new world, or every load wipes the bits it just read. *(Task 4)*
4. **Validation.** A v5 document with a bad generator, a run-length array of the wrong length or coordinates past the border is refused, not half-loaded. *(Task 2)*
