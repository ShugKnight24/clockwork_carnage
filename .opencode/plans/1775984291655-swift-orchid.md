# Clockwork Carnage: Modularization & Performance Plan

## Current State (Brutal Assessment)

**game.js is an 11,436-line god object.** It owns game state, update loop, rendering dispatch,
input handling, all UI rendering (menus, HUD, dialogs, character creator), save/load, mode management,
player logic, enemy AI, physics, collision detection, weapons, powerups, level transitions, achievements,
ARIA comms, kill streaks, death handling, and more. The constructor alone is ~300 lines of state
initialization. The `update()` method is a cascading if/else by GameState. The `render()` method is
another cascading if/else. There are 80+ methods. The file has a TODO on line 73 that says
"Rethink this entire file." We're going to do exactly that.

**data.js (7,325 lines)** has every piece of game content in one file. Good separation of data from
logic, but impossible to navigate.

**renderer.js (5,342 lines)** mixes raycasting core, texture generation, sprite rendering, floor/ceiling,
lighting, particle rendering, and visual effects.

**No build tool** means no TypeScript, no tree-shaking, no code splitting, no minification.
Every file loads raw over the network.

**No spatial partitioning** -- collision checks are O(n) linear scans every frame. Enemy AI checks
`isPassable` 6+ times per enemy per frame with inline grid lookups.

**Canvas 2D only** -- performance ceiling is real. Resolution scaling exists for mobile (capped at 1280)
but no dynamic quality adjustment based on actual FPS.

## Architecture: Strangler Fig Extraction

The Game class becomes a **thin orchestrator** (~800-1,200 lines) that owns the game loop and
delegates to extracted systems. Each system is self-contained, testable, and communicates through
a shared `GameContext` interface -- not by reaching into `this.game.*`.

**Goal:** Build tooling + TypeScript without changing any game logic.

**Vite rationale:** In dev, Vite serves native ES modules -- feels identical to current setup.

You get: TypeScript, tree-shaking (dead code removal), minification (~40% size reduction),
code splitting (load builder/editor only when needed), HMR for instant dev feedback.

**Verification:** Run all existing Playwright tests. Game must be 100% identical.

**Goal:** Create the type foundation that all extractions depend on.

| # | Task | Files | Size |

| 1.5 | Extract constants | `src/constants.ts` | S |

**`GameContext` is the key interface.** Extracted systems receive a context object instead of
a reference to the entire Game class. This breaks the circular dependency cycle.

```typescript
interface GameContext {
  player: Player
  entities: Entity[]
  map: GameMap
  time: number
  deltaTime: number
  timeScale: number
  settings: GameSettings
  audio: AudioManager
  mode: GameMode
}
```

Systems call `ctx.player.x` not `this.game.player.x`. They can't reach into arbitrary game state.

### Phase 5: Performance Optimization (~4 days)

#### 5.1 Adaptive Resolution Scaling

The biggest single perf win. Currently resolution is fixed (capped at 1280 on mobile).
Instead: dynamically adjust render resolution to maintain 60 FPS.

```typescript
class AdaptiveQuality {
  targetFPS = 60
  renderScale = 1.0        // 1.0 = native, 0.5 = quarter pixels
  minScale = 0.4
  maxScale = 1.0

  adjust(currentFPS: number) {
    if (currentFPS < this.targetFPS - 5) this.renderScale *= 0.95
    else if (currentFPS > this.targetFPS - 2) this.renderScale *= 1.02
    this.renderScale = clamp(this.renderScale, this.minScale, this.maxScale)
  }
}
```

The game canvas renders at `width * renderScale` and CSS scales it up. This is how most
Canvas 2D games handle variable hardware. **Expected impact: 2-4x FPS improvement on low-end.**

| File | Change |
|------|--------|
| `src/utils/perf.ts` | AdaptiveQuality class |
| `src/main.ts` | Apply render scale on resize and per-frame adjustment |
| `src/rendering/renderer.ts` | Use scaled dimensions |

#### 5.2 Spatial Hash Grid

Replace O(n) entity iteration with O(1) spatial lookups.

```typescript
class SpatialGrid {
  cellSize = 2  // 2 map tiles per cell
  cells: Map<number, Entity[]>

  insert(entity: Entity): void
  query(x: number, y: number, radius: number): Entity[]
  clear(): void
}
```

**Impact:** Enemy-player distance checks, projectile-entity collision, pickup collection
all become O(k) where k is nearby entities instead of O(n) total entities.

| File | Change |
|------|--------|
| `src/utils/spatial-grid.ts` | SpatialGrid implementation |
| `src/systems/physics.ts` | Use grid for collision queries |
| `src/systems/combat.ts` | Use grid for hit detection |
| `src/systems/ai.ts` | Use grid for proximity checks |

#### 5.3 Object Pooling

Particles, projectiles, and damage numbers are created/destroyed frequently. GC pressure
causes frame spikes.

```typescript
class ObjectPool<T> {
  pool: T[] = []
  create: () => T
  reset: (obj: T) => void

  acquire(): T { return this.pool.pop() ?? this.create() }
  release(obj: T) { this.reset(obj); this.pool.push(obj) }
}
```

| Target | Current | With Pool |
|--------|---------|-----------|
| Particles | `new` on spawn, GC on death | Pool of 500, reuse |
| Projectiles | `new` on fire, GC on hit | Pool of 100, reuse |
| Damage numbers | `new` on damage, GC on fade | Pool of 50, reuse |

#### 5.4 Texture Caching

Currently `generateTextures()` creates textures at startup and regenerates floor/ceiling
textures on act change. This is fine. But ensure:
- Textures are only generated once per configuration
- Floor/ceiling buffer is cached and only invalidated on resize or act change
- No per-frame texture generation anywhere

#### 5.5 Render Pipeline Optimization

- **Skip offscreen entities:** Already partially done via raycaster, but sprite sorting
  should cull entities behind the camera entirely before processing
- **Batch Canvas 2D calls:** Group `fillRect`, `drawImage` calls by style to reduce
  context state changes
- **Reduce `save()`/`restore()` pairs:** Each pair costs ~0.5ms. The HUD alone likely
  has 20+ pairs. Use manual state management for hot paths.
- **Offscreen canvas for HUD:** Render HUD to offscreen canvas, composite once per frame.
  HUD only needs re-rendering when state changes, not every frame.

#### 5.6 Mobile-Specific Optimizations

| Optimization | Impact |
|--------------|--------|
| Halve particle count | Fewer draw calls |
| Reduce draw distance from ~20 to ~12 tiles | Fewer wall strips |
| Skip floor/ceiling texture rendering (use flat color) | Major savings |
| Reduce entity update rate to 30Hz (render at 60) | Half the AI/physics cost |
| Disable vignette + scanline overlays | Save 2 full-screen composites |

## Verification Strategy

After **every single extraction:**

1. `npx playwright test tests/smoke.spec.js` -- game loads, modes work
2. Manual play-test: start arena round 1, kill enemies, die, restart
3. Manual play-test: start campaign, play through cutscene, complete level 1
4. Check browser console for errors
5. Compare FPS before/after on same hardware

After **Phase 5 (performance):**

1. Run game on throttled CPU (Chrome DevTools, 4x slowdown)
2. Measure FPS with Profiler overlay in: arena round 5+ (many enemies), campaign level with effects
3. Compare before/after screenshots for visual regression
4. Test on actual mobile device (or responsive mode in DevTools)

After **all phases:**

1. Full Playwright suite: `npx playwright test`
2. Performance benchmark: sustained 60 FPS on MacBook Air equivalent
3. Mobile performance: sustained 30+ FPS on mid-range phone
4. Bundle size comparison: original vs. `vite build` output

## Future Considerations (Noted, Not In Scope)

- **Mobile controller support:** Gamepad API on mobile browsers (Phase 5.6 lays groundwork)
- **WebGL renderer:** Canvas 2D has a perf ceiling. A WebGL backend using the same
  RenderPipeline interface would be the ultimate performance unlock. The renderer
  decomposition (Phase 4) makes this possible without rewriting the game.
- **Web Workers for AI:** Move enemy AI to a worker thread for zero main-thread impact.
  Requires serializable game state, which the TypeScript types enable.
- **Multiplayer:** The `js/net/` stubs exist. The system extraction (Phase 3) creates
  the server-authoritative architecture needed for real multiplayer.
- **Editor integration:** The `js/editor/` scaffold can be wired up once the game
  systems are modular and expose clean APIs.

## Key Decisions

1. **Vite over zero-build:** Dev gets TypeScript + HMR. Production still outputs static
   files. Users still open index.html. Net zero cost, massive dev velocity gain.

2. **GameContext over god object:** Systems receive typed context, not the entire Game
   instance. Prevents re-coupling after extraction.

3. **Strangler Fig, not Big Bang:** Game stays playable after every extraction. Risk is
   bounded per change. Tests catch regressions immediately.

4. **Adaptive resolution over fixed caps:** The single highest-impact perf optimization.
   Automatically scales to any hardware.

5. **TypeScript migration is incremental:** `allowJs: true` means we rename files one at
   a time. No big-bang type migration. Each file gets types when it gets extracted.
